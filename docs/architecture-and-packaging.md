# 저장소 구조와 테마별 배포

상태: 공통 구조 제안과 테마 하네스 1차 구현. `JW BUSINESS 01`의 홈·공통 내부 레이아웃·구조 프리셋·문의 흐름을 개발 ZIP으로 만들어 로컬 G7 설치와 편집 저장·재진입을 확인했습니다. G7 `layout-strategy=keep` 업데이트가 고객 수정 레이아웃을 유지하는 것도 실증했습니다. 데이터 팩 설치·제거 보존 검증 뒤 판매 출시본을 확정합니다. 공통 UI 패키지는 두 번째 테마에서 실제 재사용을 확인한 뒤 확장합니다.

## 개발 구조

```text
packages/
  foundation/           토큰 규격·기본 UI·접근성 동작
  g7-adapter/           공개 호스트 연결
  assets/               재배포 가능한 공통 자산
tools/theme_harness/    Python 생성·설정·검사·빌드·패키징
templates/theme-scaffold/
theme-stack.json        허용 기능·정확 버전·배포 포함 규칙
themes/<theme-family>/<identifier>/
  product.md
  design/               선택 도안·토큰·섹션 규칙
  template.json
  routes.json
  components.json
  editor-spec.json
  layouts/
  src/
  assets/
  tests/
```

G7에 설치되는 폴더는 `templates/<identifier>`이며 저장소의 테마군 디렉터리는 개발용 분류입니다.
G7 manifest에 없는 필드를 임의로 넣지 않습니다. 상품·제작 메타데이터는 product 문서나 별도 제작 설정에 둡니다.

## 구현 언어와 런타임

- TypeScript/React: 컴포넌트와 상호작용. G7 공유 React 계약 사용.
- JSON: 실제 G7 route/layout/component/editor-spec 선언과 별도 제작용 토큰.
- CSS: 테마별 표현. 허용 토큰·공통 컨트롤 사용.
- Python: 검사 범위·실행·패키징 제어. 셸은 짧은 실행 진입점만.
- Node/Vite: 로컬·CI에서 브라우저 자산 빌드. 정확한 도구 버전은 첫 구현 때 G7과 맞춰 고정.

현재 조사된 G7 템플릿은 `dist/js/components.iife.js`, `dist/css/components.css`와 manifest/spec을 사용합니다.
네이티브 편집기 자산 탐색과 공개 페이지 asset 로드가 동일하다고 추정하지 않고 대표 구현에서 둘 다 연결합니다.
private renderer/registry를 import하거나 G7 코어 구현을 테마 소스 안에 복제하지 않습니다.

## 판매 전달물

```text
<identifier>-<version>/
  install/<identifier>.zip
  developer/            테마 소스·필요 공통 소스·규칙·관련 하네스/시험
  docs/                 설치·편집·업데이트·지원 조합
  asset-licenses/        에셋 및 제3자 고지
  CHANGELOG.md
```

개발 시에는 중앙 원본을 참조하고 패키징 때 해당 버전의 필요한 파일을 포함합니다.
설치 ZIP에는 runtime 자산만 넣습니다. 개발 하네스는 별도 developer 폴더에 전달하며 웹 서버 실행 의존성이 아닙니다.
개발 키트에는 재현에 필요한 버전·잠금 파일·실행 안내를 포함하되 개인 경로·계정·비밀 값·다른 테마는 제외합니다.
테마 내부 에셋 경로는 다른 테마 폴더나 저장소 상위 경로를 참조하지 않습니다.

## 버전·업데이트

### 테마·프로필·데이터 팩·기능 모듈의 구성

상품 구성은 [분야 체계와 제작 정책](field-taxonomy-and-layout-data-policy.md)의 네 요소를 따릅니다.

| 요소 | 전달·버전 경계 | 데이터 소유권 |
|---|---|---|
| 테마 | 디자인·공통 페이지·편집 규칙·모듈 화면 연결을 테마 버전으로 제공 | 고객 편집 원본은 G7 소유 |
| 레이아웃 프로필 | 메뉴·활성 페이지·섹션 조합. 초기에는 팩에 포함하고 호환 테마 버전 명시 | 설치 후 메뉴·페이지는 고객 G7 소유 |
| 업종 데이터 팩 | 프로필·문구·이미지·게시물·상품 관계를 묶고 테마와 별도 버전 관리 | 설치 후 G7 및 해당 모듈 소유 |
| 기능 모듈 | 기존 지원 모듈 또는 별도 개발 제품. 이름·버전·설치 조건·연결 화면 명시 | 예약·주문·매물 등 업무 원본과 처리 규칙은 해당 모듈 소유 |

프로필은 초기부터 독립 배포 시스템으로 만들지 않습니다. 업종 데이터 팩에 포함해 시작하고, 지원 테마·프로필 식별자·필요 모듈·포함 페이지를 제작 메타데이터에 기록합니다. 실제 팩 필드와 스키마는 첫 설치 실증에서 확정하며 G7 manifest에 임의 필드를 추가하지 않습니다.
예를 들어 BUSINESS 테마와 제조업 팩을 사용하는 사이트에 IT 팩을 추가한다고 테마 코드나 기존 고객 데이터를 교체하지 않습니다. 신규 설치와 기존 사이트에 페이지를 추가하는 흐름을 구별하고 대상·충돌·생성된 데이터의 연결을 확인합니다.
기능 모듈이 필요한 팩은 설치 전 의존성을 확인합니다. 모듈 미설치 상태에서는 기능형 설치를 중단하거나 명시적으로 제공된 기본형 팩을 선택하며, 자동으로 성공 화면만 제공하지 않습니다.

### 업데이트 보존 원칙

분야별 레이아웃 데이터는 테마 버전과 별도로 관리합니다. AI로 사전 제작·점검한 JSON·최적화 이미지 원본과 분야별 Release ZIP을 제공하고, 독립 G7 모듈이 완성 팩을 삽입합니다. 저장소·업데이트·하네스 경계는 [설치 모듈·배포 구현계획](layout-data-module-and-release-plan.md)을 따릅니다. 벤치마크 모듈·데이터·생성 코드는 활용 대상에서 제외합니다.
설치된 콘텐츠와 파일은 G7 및 해당 기능 모듈이 소유합니다. 테마 ZIP이나 모듈 업데이트가 고객 데이터를 자동 재설치·삭제하지 않습니다.

- 테마 버전은 독립적이며 공통 기반 버전도 각 테마가 명시적으로 채택합니다.
- 공통 라이브러리 수정이 이미 판매한 ZIP을 바꾸지 않습니다. 변경은 새 버전으로 제공합니다.
- G7·편집 확장·모듈 지원 조합을 실제 시험 범위대로 명시합니다.
- 고객 업데이트는 G7 `template:update ... --layout-strategy=keep`을 기본으로 안내합니다. 로컬 G7에서 수정된 홈 레이아웃의 내용·잠금 버전이 유지되는 것을 확인했습니다. `overwrite`는 고객이 기본 레이아웃으로 초기화할 때만 사용합니다.
- 초기 자동 업데이트 서버·DRM·판매자 공통 CDN 의존성은 만들지 않습니다. 배포 채널과 상품 약관은 후속 결정입니다.
